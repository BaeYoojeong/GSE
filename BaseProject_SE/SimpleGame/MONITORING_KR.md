## 실행

1. 기존 Visual Studio 솔루션에서 SimpleGame을 빌드한다. 프로젝트가 HTML/CSS/JS를 실행 파일 옆 `Monitor` 폴더에 복사한다.
2. 게임을 실행한다. 콘솔에 `[monitor] Local dashboard: http://127.0.0.1:8765/`가 표시된다.
3. 같은 PC의 브라우저에서 `http://127.0.0.1:8765/`를 연다. 별도 Python·Node 설치나 외부 서비스가 필요 없다.
4. JSON 원문은 `http://127.0.0.1:8765/api/state`에서 확인한다.

HTML 파일을 파일 탐색기에서 직접 여는 대신 위 HTTP 주소를 이용한다. 웹 페이지는 같은 서버의 JSON을 약 1초 간격으로 받는다. 게임이 종료되면 서버도 종료되며 대시보드는 연결 끊김을 표시한다. 웹 화면을 다시 열어도 실행 중 게임의 최근 사건을 수신한다.

브라우저로 전환해도 게임 시뮬레이션은 계속 진행한다. 게임 입력을 해제하고 백그라운드에서 약 20ms 간격으로 상태를 갱신하며 불필요한 화면 재그리기는 요청하지 않는다. NPC와 몬스터의 전투도 진행될 수 있다.

포트를 바꾸려면 게임 프로세스의 환경 변수 `ASHEN_MONITOR_PORT`를 지정한다. 예: `8766`이면 `http://127.0.0.1:8766/`. `0`이면 HTTP 모니터를 비활성화한다. 기본 포트가 사용 중이면 콘솔에 실패 이유를 표시하고 게임은 계속 실행한다. 외부 PC 접속은 제공하지 않고 IPv4 루프백에만 연결을 받는다.

## 마을 분위기 산정

마을 이름 옆 분류는 현재 주민과 최근 사건에서 계산하는 모니터링 지표다. 주민의 실제 직업이나 AI 가중치를 이 화면에서 수정하지 않는다. 현재 육상 월드에서 '해적 마을'에 해당하는 성격은 **약탈자 마을**로 표현한다.

- 약탈자 비율 = 약탈자 직업 주민 / 전체 주민.
- 평균 약탈 성향 = 주민 raidWeight 평균.
- 폭력 지수 = `clamp(최근 살인 × 30 + 최근 약탈 × 6 + 적대 주민 비율 × 30, 0, 100)`.
- 안전 지수 = `100 - clamp(평균 약탈 성향 × 45 + 약탈자 비율 × 30 + 폭력 지수 × 0.6, 0, 100)`.

분류 우선순위:

1. 폭력 지수 60 이상: 분쟁 중.
2. 약탈자 비율 34% 이상 또는 평균 약탈 성향 0.55 이상: 약탈자 마을.
3. 최근 살인 존재: 흉흉한 마을.
4. 상인 비율 40% 이상: 상업 마을.
5. 구도자 비율 40% 이상: 수련 마을.
6. 평균 약탈 성향 0.2 미만이며 최근 약탈 없음: 선량한 마을.
7. 사냥꾼 비율 50% 이상: 사냥꾼 마을.
8. 나머지: 혼합 마을.

최근 통계는 시뮬레이션 시간 기준 최근 120개의 1초 구간이다. 마을별 독립된 버킷에 살인·약탈·거래를 집계하므로 사냥 로그가 많이 발생해도 사건 표시 목록에서 빠졌다는 이유로 분위기 집계에서 사라지지 않는다. 재실행 시 최근 사건 지표는 새로 시작한다.

## 사망과 소문

NPC의 즉시 부활 이전에 `murder` 또는 `death` 사건을 생성한다. 플레이어나 다른 NPC가 죽인 경우 살인, 사냥 중의 죽음 등은 일반 사망이다. 동시에 서로 죽은 NPC의 공격자 ID도 보존하며, 기존 재산 이전과 부활 규칙을 적용한다.

살인 현장의 실제 위치에서 180단위 안에 있는 살아 있는 NPC를 소속 마을과 관계없이 목격자로 센다. 피해자와 공격자를 제외하고 한 명 이상이면 별도 `murder_rumor` 사건을 생성한다. `confirmed=false`, `witness_count`, `source_event_id`로 원본 확정 사건과 연결한다. 소문을 살인 통계에 다시 더하지 않는다.

현재 소문은 사건 감시용 파생 기록이다. 목격자 간 대화 전파, 거짓 정보, 신뢰도 변화, 평판과 AI 의사결정 반영은 후속 확장 사항이다. 목격자 판정은 거리 기준이며 건물 시야 가림을 계산하지 않는다.

사건 목록은 실행 중 최근 512건을 보관한다. 기존 프로파일러 사건 CSV에는 같은 구조의 식별 정보도 남긴다. 모니터 사건 버퍼와 최근 통계는 세이브에 쓰지 않는다. `ASHEN_WORLD_V4 / SOCIETY_V4`에는 주민의 거점 기준 이동 좌표와 여섯 사냥터를 기록하며 기존 SOCIETY_V1/V2/V3 저장도 불러온다.

## JSON 계약과 수신 방식

`GET /api/state` → `application/json; charset=utf-8`, `Cache-Control: no-store`.

최상위 구조:

```text
schema_version: 1
session_id: 실행마다 바뀌는 문자열
sequence: 실행 안에서 증가하는 스냅샷 순번
generated_at_ms: 생성 시각 (Unix 밀리초)
simulation_seconds: 게임 시뮬레이션 시각
game: running, player_dead, pk_enabled
totals: 전역 NPC·마을·몬스터·활동 카운터
villages[]: id, name, chunk, loaded, mood, population, economy, monsters, activities, recent
npcs[]: 주민 상태와 행동 점수
events[]: 오래된 것부터 정렬된 최근 사건
event_window: oldest_id, newest_id, retained, capacity, recent_seconds
warnings[]: 집계 범위와 저장 상태 설명
```

NPC ID, 삶 ID, 사망 횟수, 사건 ID와 청크 좌표는 큰 정수의 JavaScript 정밀도 손실을 피하기 위해 문자열로 전송한다. 마을 ID는 `x,y` 문자열이다. `actor_id="0"`은 플레이어이거나 행위자가 없는 시스템 사건이므로 사건 종류/본문과 함께 해석한다. 사냥터 슬롯 번호를 NPC ID로 보내지 않는다. 원본이 없는 `source_event_id`와 지역이 없는 `village_id`는 null이다.

매 메시지는 완전한 스냅샷이다. 연결 재개 시 누락된 상태를 부분 패치로 복구할 필요가 없다. 사건 ID는 session_id 안에서만 유효하다. 새 session_id를 받으면 이전 실행의 선택/이벤트 이력을 초기화한다. sequence가 갱신되지 않거나 생성 시각이 오래되면 화면에서 지연 상태를 알린다.

HTTP 작업자는 SceneGraph나 NPC 기록에 접근하지 않는다. 게임 스레드가 JSON을 완성한 뒤 불변 문자열을 전달하고, 작업자는 그 스냅샷만 읽는다. 느린 브라우저의 소켓 전송이 게임 프레임을 기다리게 하지 않는다. 데이터 수집/직렬화 자체는 게임 스레드에서 수행하며, `monitor_snapshot` 프로파일 이벤트로 바이트 수와 CPU 시간을 측정한다.

초기 프로토타입에서는 전체 스냅샷을 전송한다. NPC가 크게 증가하면 갱신 주기 조절, 페이지별 API, 변경분 전송 등을 검토한다. 이벤트 버퍼는 512건, 마을 최근 통계는 마을당 120칸으로 제한한다. 외부 글꼴·라이브러리·CDN은 사용하지 않는다.

## 주민의 실제 위치와 외출

`village_id`는 소속 마을, 기존 `position`은 소속 마을을 원점으로 하는 좌표다. 새 `location.chunk`와 `location.local`은 실제 청크와 지역 좌표이며 음수 방향 이동도 정규화한다. `away_from_home`, `destination`, `destination_kind`, `journey`, `goal_dwell_seconds`를 추가했다. 마지막 필드는 목적지에서 남은 체류 시간이다.

마을 `population.total`은 소속 주민 수다. `present`는 마을 안 생존 주민, `away`는 외출 생존 주민, `visitors`는 다른 마을 소속 방문객이다. 모든 수가 같은 소속 기준은 아니므로 합계를 전체 NPC로 해석하지 않는다. 야외 방문 때문에 새 마을을 생성하지 않는다.


## 약탈 성공과 이동 유지 관찰

주민 상세에 `raid_phase_label`, `raid_cooldown_seconds`, `successful_raids_session`, `stolen_coins_session`, `last_raid_target`, `last_raid_amount`를 표시한다. 성공 카운터는 실제 동전 이전 때만 증가하며 이번 실행 범위다. 기존 상단 `totals.raids`는 저장된 누적 수다. `travel_commit_seconds`, `destinations_reached_session`, `in_wilderness`로 이동 계획과 실제 야외 활동을 구분한다. `destination_kind=patrol`은 약탈 대상 탐색 동선이다. 세부 규칙은 WILDERNESS_RAID_BALANCE_KR.md 참조.
