## 1. 최종 산출물

완성할 것은 “개별 기능이 들어 있는 샘플”을 넘어, 다음 경험을 하나의 저장 세계에서 이어서 플레이할 수 있는 프로토타입이다.

> 시작 → 학습 → 탐험/전투/성장 → 지역 복구 → 선택 또는 실패에 따른 죽음과 전승 → 재회 → 보스와 종탑 사건 → 완료 화면 → 탐험 계속 → 종료/재실행 후 변화 유지.

죽음은 첫 이야기 완료의 강제 조건이 아니다. 다만 **프로토타입 검수에서는 사망·전승·재회와 저장 복원을 반드시 확인한다.**

산출물 목록:

| 종류 | 내용 |
|---|---|
| 게임 | 첫 이야기와 완료 후 탐험이 가능한 실행 패키지 |
| 코드 | Actor/SceneGraph 기반, 책임별 모듈, 외부 셰이더, 프로젝트 등록 |
| 콘텐츠 | 4개 의미 장소, 주민 3명, 일반 적 2종, 보스 1종, 대화/목표/최소 오디오 |
| 데이터 | 신규 저장 스키마, 이전/백업, 공유 자원 정책, 전승·보상 중복 방지 |
| 진단 | 실행 로그, 분석 스크립트, 기준선/개선 세션 비교 |
| 문서 | 기획/구조/조작/검수/알려진 제한/변경 기록 |

현재 소스의 모든 변경이 이미 커밋되었다고 가정하지 않는다. 구현을 시작할 때 작업 트리와 `dev` 상태를 먼저 확인하고 기존 변경을 보존한다. 커밋·푸시는 별도 요청 범위에 따른다.

## 2. 상태와 우선순위 표기

- **기존 코드 있음:** 재사용할 구현이 있다. 실행 검수 완료를 의미하지 않는다.
- **신규/보강:** 이 기획에 따라 추가하거나 수정할 작업이다.
- **완료:** 기능 구현, 연결, 필요한 데이터 이전, 사용자 실행 검수 근거가 모두 존재한다.
- **P0:** 첫 프로토타입 완료에 필수.
- **P1:** 첫 이야기 이후의 사용성/콘텐츠 확장.
- **P2:** 장기 월드/대규모 게임을 위한 구조 확장.

본 계획의 체크박스는 현재 모두 미완료 상태로 시작한다. 임의로 통과 표시하지 않는다.

## 6. 성능 확인 계획

### 6.1 재현 가능한 세션

각 시나리오에서 해상도, GPU/드라이버, Release/Debug, 후처리, 창 포커스, 콘솔 빈도, 세이브/시드, 이동 경로를 기록한다. 서로 다른 하드웨어 수치를 한 표에서 단순 평균하지 않는다.

| 세션 | 조건 | 알아낼 것 |
|---|---|---|
| S0 기본 대기 | 같은 쉼터에서 고정 카메라 | 안정 상태 생성·업로드·UI 비용 |
| S1 정해진 이동 | 첫 지역→수도원 동일 경로 | 생성/스트리밍 순간 지연 |
| S2 전투 | 같은 적 수·이펙트·전승 지원 | Actor·발사체·배치 증가 |
| S3 웜 캐시 | S1을 재실행 | 파일 적중과 형상 생성 감소 |
| S4 큐 단일 제출 | `ASHEN_BATCHING=0` | 동일 새 렌더 경로에서 배치 유무 비교 |
| S5 후처리 비교 | Bloom/블러 설정별 | post_calls와 CPU 비용 변화 |
| S6 장기 표본 | 방문 100청크·삶 50개 | 활성 메모리와 영구 데이터 증가 구분 |

S4는 변경 전 렌더러 자체가 아니다. 새 사각형 인스턴스들을 한 개씩 제출하므로, 이전 코드와 비교할 때는 별도의 이전 빌드 기준선이 필요하다.

### 6.2 목표와 통과 판정

| 항목 | 제안 목표/판정 | 주의 |
|---|---|---|
| 장치/해상도 | M0에서 기준 PC와 해상도를 정해 기록 | 아직 특정 PC의 성능을 보장하지 않음 |
| 프레임 | 기준 PC Release에서 60FPS를 목표 | 기존 CPU 렌더 로그만으로 GPU 프레임 예산을 판단하지 않음 |
| draw call | 동일 큐 단일 제출보다 배치 실행의 평균 호출 수 감소 | 목표 30% 이상은 튜닝 지표, 실제 결과를 기록 |
| 반복 메시 생성 | 같은 표시 형상의 웜 구간에서 불필요한 재생성 없음 | 새 청크/새 포즈 최초 생성과 구분 |
| 캐시 한도 | GPU/파일 캐시가 설정 한도 안에서 작동 | 로그/세이브 용량과 별개 |
| 정점 패딩 | 배치별 submitted/useful ≤ 2 | 낮은 호출 수가 높은 GPU 속도를 보장하지 않음 |
| 긴 꼬리 지연 | p95/최대와 cold/warm 원인을 보고 | 평균값만으로 순간 멈춤을 숨기지 않음 |
| 회귀 | 동일 조건 3회에서 반복되는 지연 악화가 있으면 원인·조치 기록 | 노이즈와 재현 가능한 회귀 구분 |

프로토타입 완료를 위해서는 미측정 상태를 통과로 처리하지 않는다. 기준 PC가 정해지지 않았거나 렌더 오류가 있으면 성능 완료 항목을 열어 둔다. 비동기 GPU timer query는 GPU 병목을 판정할 때 추가하며, 매 프레임 glFinish로 측정값을 왜곡하지 않는다.

## 10. 작업 운영 규칙

현재 요청의 산출물은 기획 문서다. 구현을 시작할 때 M0부터 진행하고 기존 자산을 보존한다. 사용자의 기존 지시에 따라 별도 요청이 없으면 빌드·게임 실행·렌더링 결과 확인은 사용자가 담당한다. 코드 구현자는 정적 점검과 검수 절차를 제공하고, 사용자가 전달한 결과를 근거로 문제를 수정한다.

구현 범위를 늘릴 때는 먼저 P0 완료에 필요한지 판단한다. 새 기능의 재미를 이유로 저장/전승/진행 막힘 같은 기본 검수를 미루지 않는다. 기획 변경이 필요한 경우 변경 내용·이유·범위·완료 기준을 문서에 남겨 다음 작업이 같은 기준을 사용하도록 한다.
