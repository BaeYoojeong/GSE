재의 계승 렌더링 개선 리포트 — 배치 / 파일 캐시 / 인스턴싱
작성: 2026-09-28

1. 결론과 검증 수준

현재 실행되는 DarkAgeRenderer에 순서를 보존하는 배치 큐를 추가했다.
모델마다 즉시 draw하던 경로를, GPU 메시 아틀라스와 인스턴스 버퍼를 이용해
glDrawArraysInstanced로 제출하는 경로로 바꿨다.
체력바, 공격 예고, 피격 표시, 조준/상호작용 표시, 재 파티클은 동일한 사각형 메시를
공유하고 위치/크기/색/발광만 인스턴스 데이터로 전달한다.
절차적 모델과 공용 메시를 파일로 저장하고 다음 실행 시 로딩하는 캐시를 추가했다.

이 문서의 진단은 소스 분석에 근거한다. 비교 가능한 원본 실행 로그의 실제 수치는
이번 요청에 첨부되지 않았으며 빌드·실행·셰이더 컴파일·화면 확인을 수행하지 않았다.
따라서 FPS 상승, draw call 감소율, GPU 성능 향상을 측정 결과로 주장하지 않는다.
아래 로그와 비교 도구는 사용자가 실행한 뒤 실제 효과를 검증하기 위한 것이다.

2. 기존 경로에서 확인한 비용

  A. 메시 캐시 적중과 draw call 감소는 별개였다.
     DrawCachedMesh → MeshCache::Draw가 오브젝트마다 glDrawArrays를 호출했다.
     이미 만들어진 메시를 써도 모델/그림자/UI마다 별도의 제출 비용이 발생했다.

  B. 반복 생성되는 기하가 있었다.
     적 체력바/공격 예고, 피격 효과, 조준 표시와 재 파티클은 Rect/Tri를 호출해서
     정점을 다시 채운 뒤 glBufferData(GL_STREAM_DRAW)로 업로드했다.
     모양은 사각형인데 위치, 크기와 색이 달라질 때마다 정점을 생성한 셈이다.

  C. 메모리 캐시만 존재했다.
     종료 후 다시 실행하면 모델을 다시 생성했다. LRU 한도를 넘은 모델도 다시 만들었다.
     새 지역이나 새 애니메이션 형상의 최초 생성과 캐시 문제에 의한 반복 생성을
     기존 draw_calls 한 항목만으로는 구분할 수 없었다.

  D. 서로 다른 렌더링 비용이 하나의 숫자에 섞여 있었다.
     후처리의 전체 화면 패스, 월드 오브젝트, HUD가 같은 draw_calls에 포함됐다.
     어느 경로에서 호출 수가 늘었는지, 생성/업로드가 얼마나 발생했는지 알 수 없었다.

3. 이번 구현

3-1. 배치 큐: RenderBatch.h / RenderBatch.cpp

  Submit(mesh, instance, texture)로 그리기 요청을 누적한다.
  모델/그림자/단위 사각형은 GPU Texture Buffer Object의 공통 아틀라스에 보관한다.
  World.vs는 각 인스턴스의 시작 정점과 정점 수를 받아 texelFetch로 형상을 읽는다.
  같은 배치 안에서도 서로 다른 메시를 사용할 수 있다.
  그래서 단순히 동일한 메시가 연달아 나오는 경우에만 묶는 방식보다 적용 범위가 넓다.

  인스턴스 1개는 64바이트다.
    월드/화면 위치, 스케일, 색상, 투영 종류, 투명도, 발광 강도,
    메시 시작/길이, 화면상의 로컬 오프셋을 포함한다.
  정점 전체를 매번 복사하는 대신 이 작은 데이터만 스트리밍한다.
  매 프레임 인스턴스 버퍼 업로드는 여전히 필요하며, 이것은 메시 형상 재생성과 다르다.

  배치는 다음 조건에서 실제 draw로 제출된다.
    - 텍스처가 바뀜: texture
    - 인스턴스 1,024개: capacity
    - 예상 정점 패딩 비율이 2배 초과: vertex_padding
    - 지형/그림자/월드 패스 경계: pass_end
    - 후처리 진입: before_post
    - UI까지 완료: frame_end
    - 캐시 공간 확보: cache_pressure
    - 캐시 입장 실패에 대한 기존 스트리밍 경로: fallback
    - 큐가 참조하는 텍스처가 삭제되기 전: text_eviction
    - 배치 비교 모드: comparison_mode

  framebuffer, shader 전체에 적용되는 uniform, 텍스처 수명에 관한 상태 변경 전에
  큐를 비운다. 각 요청의 순서는 유지한다. 알파 블렌딩 대상들을 메시 종류만으로
  재정렬하면 건물 가림, 그림자, 발광의 앞뒤 관계가 달라지므로 그런 정렬은 하지 않는다.
  지형 → 접지 그림자 → 깊이순 월드 → 후처리 → 재/HUD 순서가 유지된다.

3-2. 정점 패딩의 비용과 상한

  하나의 인스턴싱 호출은 동일한 정점 개수를 각 인스턴스에 적용한다.
  서로 다른 형상을 묶을 때 배치의 최대 정점 개수를 사용하며,
  더 짧은 메시의 초과 정점은 셰이더에서 아틀라스를 읽기 전에 화면 밖의 퇴화 삼각형으로 처리한다.
  모든 메시 길이는 삼각형 단위인 3의 배수인지 검증한다.

  submitted_vertices = 배치 최대 정점 수 × 인스턴스 수
  useful_vertices = 해당 배치에 실제 필요한 정점 수의 합
  padding_ratio = submitted_vertices / useful_vertices

  이 비율이 2를 넘으면 배치를 나눈다. 호출 수를 줄이는 대신 정점 셰이더 작업량과
  TBO 접근 비용이 늘 수 있으므로 GPU가 빨라진다고 단정할 수 없다.
  향후 GPU timer query로 검증하고 필요하면 한도를 낮추거나 동일 메시 배치를 병행할 수 있다.

3-3. GPU 캐시: MeshCache

  메시별 VAO/VBO 대신 공유 아틀라스를 사용한다.
  정점 1개는 RGBA32F 텍셀 3개(48바이트)로 배치한다.
  한도는 GPU 아틀라스 32MiB와 상주 메시 256개이며,
  실제 장치의 GL_MAX_TEXTURE_BUFFER_SIZE가 더 작으면 그 제한에 맞춘다.
  free span을 합치고 LRU로 공간을 회수한다.
  큐가 shared_ptr로 참조 중인 메시의 영역은 재사용하지 않는다.
  공간이 부족하면 큐를 먼저 제출한 뒤 재시도한다. 그래도 실패하면 기존 동적 그리기와
  fallback_draw 이벤트로 표시하므로 조용히 오브젝트를 누락시키지 않는다.

  resident_bytes는 현재 사용 중인 아틀라스 영역 크기다.
  아틀라스의 예약 용량은 시작 시 atlas 이벤트에 기록된다.
  두 값은 다르며 드라이버 내부 전체 VRAM 사용량을 뜻하지 않는다.

3-4. 파일 캐시: DiskMeshCache

  경로: %LOCALAPPDATA%\AshenInheritance\MeshCache\geometry-3
  파일명은 기존 10개 정수 형상 키를 그대로 80자리 16진수로 표현한다.
  형상에 영향을 주지 않는 시간/위치/체력바 길이는 키에 넣지 않는다.
  모델 생성 코드 또는 투영에 의해 구워지는 형상이 바뀌면 GeometryRevision을 올려야 한다.

  메모리 적중 → 파일 로딩 → 파일이 없거나 잘못되면 생성 → GPU 등록 → 파일 저장 순서다.
  최초 실행/새 지역/새 포즈는 최초 생성 비용이 있을 수 있다.
  다음 실행에서는 동일 키의 파일을 읽어 정점 생성 작업을 생략한다.
  게임을 아직 실행하지 않았으므로 실제 .mesh 파일은 최초 실행 시 생성된다.

  헤더: magic, 파일 포맷 버전, 형상 버전, 정점 수, 전체 형상 키, 64비트 체크섬.
  파일 길이, 정점 수/상한, 유한한 float, 체크섬을 검사한다.
  손상/불일치 파일은 사용하지 않고 다시 생성한다.
  임시 파일 작성과 닫기를 확인한 후 같은 디렉터리에서 최종 파일로 교체한다.
  디스크 오류가 있어도 메모리 렌더링은 계속된다. 캐시는 저장 게임 데이터와 별개다.
  버전 디렉터리당 256MiB/4,096개 한도로 오래 사용하지 않은 캐시 파일을 정리한다.
  다른 버전 디렉터리와 과거 프로파일 세션은 자동 삭제하지 않는다.
  여러 프로세스를 동시에 실행하는 경우 전체 디스크 한도는 각 프로세스의 인덱스를 기준으로 한다.
  콜드 캐시 파일 IO는 렌더 스레드에서 동기적으로 수행된다. disk_ms로 비용을 분리한다.

4. 로그와 분석

실행할 때마다 다음 디렉터리에 기록한다.
  %LOCALAPPDATA%\AshenInheritance\Profiling\날짜-시각_PID

  frames-*.csv: 매 프레임 전체/패스별 호출 수, CPU 시간, 인스턴스 수,
    정점 패딩, 업로드 바이트, 생성 횟수, 캐시 적중/실패/퇴거, 표시/컬링, 텍스트 생성.
  batches-*.csv: 배치가 나뉜 이유와 인스턴스/정점 수.
  events-*.csv: 세션/장치/설정, 형상 키별 생성, 파일 로딩/저장/손상, 퇴거, fallback.

  빈번한 메모리 적중은 이벤트 한 줄씩 남기지 않고 프레임별 집계한다.
  파일 캐시 이벤트의 키와 mesh_build 키를 연결하면 반복 생성되는 형상을 찾을 수 있다.
  로그는 종류마다 16MiB × 4개 순환 파일로 제한한다. 세션당 최대 약 192MiB이며
  오래된 부분은 덮어쓴다. 별도 세션 디렉터리는 보관되므로 필요 없는 과거 세션은 관리해야 한다.
  120프레임마다 flush하고 정상 종료 시 닫는다. 비정상 종료 시 최근 버퍼 기록이 손실될 수 있다.

analyze_render_log.py는 표준 Python만 사용한다. 게임 빌드/실행을 하지 않는다.
  python analyze_render_log.py "현재 세션 디렉터리"
  python analyze_render_log.py "현재 세션" --baseline "비교 세션" --skip-frames 120

평균, p50/p95/최대, 캐시 적중률, 패스별 비용, 배치 분리 이유, 반복 생성 키,
오류 이벤트와 확인할 항목을 analysis-시각.txt로 새로 저장한다.
프레임 번호로 순환 파일을 정렬하며 보관 범위 안에 빠진 프레임 수를 표시한다.
표본/상황이 다른 두 실행의 비교가 통제된 성능 측정을 대신하지는 않는다.

5. 실행 시 비교 절차

  (1) 같은 저장 파일/카메라/경로/해상도/후처리 설정으로 기록한다.
  (2) 콜드 캐시 실행과 같은 경로의 재실행을 분리한다.
      재실행에서는 disk_hits가 증가하고 해당 키의 mesh_build가 줄어드는지 본다.
      이미 GPU에 올라간 형상은 memory_hits가 증가해야 한다.
  (3) ASHEN_BATCHING=0인 실행과 기본 실행을 비교한다.
      0은 새 큐의 항목을 한 개씩 제출하는 비교 모드다. 이전 코드 자체의 성능 기준은 아니다.
      특히 예전의 한 덩어리 효과 메시가 이제 여러 사각형 인스턴스이므로 비교 기준을 혼동하지 않는다.
  (4) ASHEN_PROFILE_CONSOLE_EVERY=60처럼 콘솔 빈도를 동일하게 설정한다.
      1이 기본값이며 0은 콘솔 프레임 통계만 끈다. CSV는 여전히 프레임마다 기록한다.
      로그 출력 자체의 CPU/IO 비용을 고려한다.
  (5) 생성/IO가 안정된 구간에서 calls와 cpu_render_swap_ms를 비교한다.
      이 시간은 update 시간 전체나 GPU 실행 시간이 아니다. swap/vsync 대기는 포함한다.
  (6) 건물 뒤 플레이어, 반투명 그림자 겹침, HDR/Bloom, 체력바/조준 위치,
      텍스트 표시와 캐시 손상 후 복구를 확인한다.

6. 향후 draw call 절감 후보와 선택 기준

  텍스트 아틀라스/텍스처 배열
    texture 사유와 ui_calls가 크면 우선 검토한다. 현재 문자열마다 별도 텍스처이므로
    다른 글자를 안전하게 한 배치로 묶는 데 한계가 있다. 한글 글리프 관리/배치/퇴거가 추가로 필요하다.

  지형 청크 사전 생성/비동기 디스크 캐시
    처음 방문할 때 build_ms/disk_ms가 튀면 검토한다.
    작업 스레드에서는 CPU 생성/파일 IO만 하고 OpenGL 업로드는 렌더 스레드로 전달해야 한다.

  가시성/공간 인덱스
    표시할 Actor보다 조회/컬링 비용이 더 크다면 SceneGraph 공간 검색을 개선한다.
    이번 변경에서는 같은 Actor의 OnScreen 계산을 세 패스에서 반복하던 것만 한 번으로 줄였다.

  동일 메시 인스턴싱 병행, 패딩 상한 조정
    submitted/useful 비율이 높거나 GPU vertex 처리 비용이 늘면 검토한다.
    호출 최소화와 GPU 작업 최소화는 다를 수 있다.

  Multi-draw indirect
    다수 메시의 명령 버퍼 제출을 더 줄일 수 있지만 기본 OpenGL 3.3 경로에는 그대로 적용할 수 없다.
    장치/확장 확인과 상위 버전 경로 분리가 필요하다. 이번에는 3.3 범위에서 구현했다.

  후처리 패스 조정
    post_calls가 전체의 큰 비중이면 Bloom 단계/해상도/필터를 비교한다.
    이전 패스 출력을 읽는 blur/downsample은 월드 배치처럼 임의로 한 draw로 합칠 수 없다.
    화면 품질과 샘플링 비용까지 함께 판단해야 한다.
