# 프레임 끊김 분석과 수정

## 확인한 원인

- 기존 로그에서 메시 캐시가 64MiB GPU 예산에 도달하면 정적 지형과 애니메이션 포즈가 서로 퇴거했다. 프레임 1588은 디스크 처리만 28.791ms, 렌더/스왑은 49.234ms였다.
- 모니터 상태 JSON을 게임 스레드에서 만들었다. 동일한 3,600프레임 이동 테스트의 수정 전 Debug에서는 약 90~110ms가 걸렸다.
- CSV 파일 열기·쓰기·회전·flush, 기본 매 프레임 콘솔 출력이 게임 스레드에서 실행됐다.
- glTF 포즈를 만들 때 매번 바인드 포즈 변환과 모든 정점의 원래 경계를 다시 계산했다.
- Blender current.json을 각 자산의 경로 확인마다 다시 읽고 파싱했다.
- 이전 cpu_render_swap_ms에는 시뮬레이션·저장·모니터 시간이 빠져 있었다. 렌더 로그만으로 전체 끊김을 판단하기 어려웠다.

## 변경한 구조

1. DiskMeshCache는 전용 작업자에서 스캔·읽기·체크섬·쓰기·정리를 수행한다. 최근 파일은 최대 8MiB까지 미리 읽는다. 읽기가 준비되지 않았으면 기존 생성 경로로 즉시 그려서 파일 완료를 기다리지 않는다. 형식·키·크기·유한값·체크섬 검사는 유지한다. 종료할 때 수락한 쓰기를 모두 처리한다.
2. GPU 64MiB/1,024개 예산은 유지한다. 먼저 같은 종류(정적/포즈)의 오래된 메시를 퇴거한다. 별도 CPU 메시 캐시 64MiB/4,096개에서 퇴거된 형상을 재사용한다. 모델 변경 시 콘텐츠 키가 달라지고, 렌더러 종료 시 캐시도 해제된다.
3. CSV는 전용 작업자가 64KiB 버퍼로 기록한다. 대기열은 8MiB, 작업 중 배치는 최대 약 8MiB다. 채널별 16MiB×4 순환 파일은 유지한다. 과부하 시 누락 행 수를 기록한다. 기본 콘솔 출력은 초당 1회, 프레임별 CSV 수집은 계속한다.
4. WorldMonitor는 메인 스레드에서 값만 복사하고 작업자가 JSON을 생성·발행한다. 처리 중/대기 중 스냅샷은 각각 최대 1개이며 대기본은 최신 상태로 합친다. 작업자는 실행 중인 Game이나 Actor 포인터를 참조하지 않는다. 서버 종료 전에 작업자를 정리한다.
5. 바인드 포즈의 primitive 경계는 glTF 로드 시 한 번 계산한다. 합성 모델처럼 캐시가 없는 경우 기존 계산으로 폴백한다. Blender overlay는 초당 한 번 검사하며 파싱 결과를 재사용한다. F9는 즉시 무효화한다.
6. 자동 저장은 이번 업데이트가 이미 2ms를 썼으면 다음 가벼운 틱으로 미룬다. 최대 지연은 시뮬레이션 시간 1초이며, 수동·사망·전승·종료 저장은 즉시 수행한다. NPC 갱신과 FULL 동기 커밋이 한 프레임에 겹치는 비용을 줄인다.
7. 새 작업자는 낮은 스레드 우선순위를 사용한다. 파일/작업자 시작 실패는 진단 로그를 남기고 해당 보조 기능을 끈다.

## 로그 읽는 법

`%LOCALAPPDATA%\AshenInheritance\Profiling\<세션>` 아래 CSV를 확인한다.

- `cpu_render_swap_ms`: 렌더 시작부터 스왑까지 CPU 시간.
- `update_cpu_ms`: 이벤트 처리·게임 업데이트 시간.
- `total_tick_cpu_ms`: 두 구간의 합. GPU 시간이나 FPS 자체가 아니다.
- `cpu_cache_hits`, `cpu_cache_bytes`: GPU에서 퇴거된 형상의 CPU 재사용과 현재 크기.
- `log_rows_dropped`: 로그 대기열 초과/파일 쓰기 오류로 누락된 누적 행 수.
- `frame_spike`: 워밍업 뒤 전체 틱이 16.67ms를 넘긴 프레임.
- `monitor_capture`: 메인 스레드 스냅샷 복사 시간.
- `monitor_json_worker`, `cache_io_worker`: 보조 스레드 시간. 메인 프레임 시간에 더하면 안 된다.
- `chunk_stream`, `world_save`: 동기 청크 구성과 안전한 저장에 걸린 시간.

`ASHEN_PROFILE_CONSOLE_EVERY=0`은 콘솔만 끈다. `1`은 기존처럼 매 프레임 출력하므로 성능 측정 때는 피한다. `ASHEN_MESH_DISK_CACHE=0`으로 파일 캐시를 끌 수 있다. 종료 전 CSV는 버퍼에 남을 수 있으며 정상 종료 시 배출한다.

## 검증 방법과 범위

수정 전 기준은 dev 커밋 c3159c2다. 동일 MSVC, GPU, 시드 20261110, 1120×784, VSync 0, 숨김 창으로 비교한다. 테스트는 새 절대 경로 프로필만 사용하며 실제 저장 파일은 열지 않는다. `--benchmark-stress`는 120프레임 준비 후 3,600프레임 동안 충돌을 우회해 청크를 가로지르며, 결정적 비교를 위해 원거리 작업자를 끈다. 모니터와 자동 저장은 켜져 있다. `--benchmark-world`는 원거리 작업자를 켜고 실제 시간에 맞춰 1,800프레임을 측정한다. 대기 시간은 CPU 프레임 측정에서 제외한다. 이 모드는 작업자 스케줄 때문에 화면 해시 비교에 사용하지 않는다.

최종 측정값과 빌드/기능 검증은 STUTTER_VALIDATION.json에 기록한다. 재실행:

```powershell
powershell -ExecutionPolicy Bypass -File .\Tools\RunStutterChecks.ps1 -Executable ..\x64\Release\SimpleGame.exe
```

## 측정 결과

아래 Release 이동 부하는 수정 전/후 각각 2회 결과의 중앙값이다. 두 번째 비교는 실행 순서를 뒤집었다. CPU 프레임에는 업데이트·렌더·스왑·계측 처리가 포함된다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| Release 이동 부하 중앙 프레임 | 0.893ms | 0.924ms |
| Release 이동 부하 느린 1% 경계(p99) | 4.769ms | 2.901ms |
| 각 실행 최대 프레임의 중앙값 | 12.712ms | 5.928ms |
| Debug 전체 NPC 폴백 부하 p99 | 114.496ms | 46.790ms |

Release p99는 약 39.2% 감소했다. 중앙 프레임은 약 3.5%(0.031ms) 증가하여, 캐시 복사와 작업자 조율의 작은 비용은 있다. 큰 지연을 줄인 효과와 구분해서 본다. 이동 부하 두 번 모두 16.67ms 초과는 0회였다.

원거리 작업자를 켠 최종 Release 실시간 테스트는 1,800프레임, p99 6.840ms, 최대 14.720ms, 16.67ms 초과 0회였다. 모니터 값 복사는 최대 0.390ms, 작업자 JSON 생성은 최대 17.340ms로 메인 스레드에서 분리됐다. HTTP로 210명·7개 마을과 증가하는 sequence/worker_batches를 확인했다.

**Debug에서는 끊김이 남아 있다.** 실제 원거리 작업자 모드에서도 중앙 16.019ms, p99 49.286ms, 최대 90.507ms, 16.67ms 초과 803/1,800회였다. 최적화를 끈 시뮬레이션·청크 생성·메시 변형 비용이 남아 있으므로 플레이 성능은 Release에서 확인한다. Debug를 빠르게 보이게 하려고 최적화·진단 옵션을 바꾸지는 않았다.

네 구성(x64/x86 × Debug/Release)은 경고 없이 빌드됐고 각 28개 창·입력 검사가 통과했다. 기능·저장 검사 660개가 통과했고 비동기 파일 왕복의 정점 바이트 일치, 손상 캐시 거부, 종료 시 쓰기 배출, 자동 저장 최대 지연 및 재시작 복원을 포함한다. 정지/이동 장면의 화면 해시와 프레임별 draw call 열은 수정 전과 동일했다. 테스트에서 CPU 메시 캐시는 64MiB 이내였고 로그 누락은 0행이었다.

## 남아 있는 비용과 한계

청크의 Actor 구성, GPU 업로드, SQLite FULL 동기 저장은 아직 메인 스레드에서 수행한다. 수동 저장·사망·전승·종료 저장은 성공 여부와 내구성 의미를 유지한다. Debug의 최적화되지 않은 전체 NPC 폴백 시뮬레이션과 저장은 Release보다 오래 걸릴 수 있다. 이번 변경은 모든 PC/외부 모델/드라이버에서 끊김이 없음을 보장하지 않는다. 새 모델의 대규모 재로딩은 별도 비용이 있으므로 위 이벤트로 다시 측정한다. GPU 메모리 예산 확대나 비동기 OpenGL 컨텍스트 도입은 이번 수정에 포함하지 않았다.
